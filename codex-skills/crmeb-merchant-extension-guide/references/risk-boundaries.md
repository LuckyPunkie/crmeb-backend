# 高风险边界

以下模块客户二开时必须谨慎，建议先备份、做测试环境验证，再上线。

## 订单创建

核心文件：

- `app/common/repositories/store/order/StoreOrderCreateRepository.php`
- `app/common/repositories/store/order/StoreOrderRepository.php`

风险：

- 金额计算错误
- 库存扣减错误
- 优惠券/积分重复使用
- 订单状态异常
- 多商户订单拆分错误

建议：

- 优先通过事件扩展订单创建后的逻辑。
- 必须改订单创建时，先梳理确认页和创建页两条链路。
- 保持事务边界稳定。

## 支付和退款

风险：

- 重复回调
- 支付金额不一致
- 订单状态未同步
- 退款后库存/账单/佣金未回滚

建议：

- 支付成功扩展优先用事件监听。
- 回调处理必须保证幂等。
- 不要跳过原有状态检查和账单逻辑。

## 库存

风险：

- 普通商品、秒杀、预售、拼团、助力、套餐库存逻辑不同。
- Redis 秒杀库存和数据库库存可能需要补偿。

建议：

- 改库存前先确认商品类型。
- 不要只改单一库存字段。
- 失败时确认是否需要回滚 Redis 或数据库。

## Swoole/Redis

风险：

- 常驻进程导致对象属性跨请求存在。
- 原生 Redis handler 被多个协程复用会报 socket 并发错误。
- 定时器重复注册会导致任务重复执行。

建议：

- 不长期保存 `Cache::store('redis')->handler()`。
- Redis/PDO/cache 连接从当前执行上下文获取。
- 定时器只注册一次。

## 微信/支付宝

风险：

- 普通商户、服务商、公众号、小程序、APP、H5 支付配置不同。
- 老旧迁移文件可能仍存在，编辑前要确认实际引用。

建议：

- 先追调用链，再改服务类。
- 支付证书、回调地址、商户号、小程序 appid 要分清。
